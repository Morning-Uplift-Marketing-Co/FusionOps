# FBIS Risk Weight Analysis & Tuning Guide

## Current Risk Formula

```python
verdict_score = int(
    proxy_risk           * 0.25 +
    (100 - isolation_score) * 0.30 +
    (100 - traffic_quality) * 0.25 +
    timeline_risk        * 0.20
)
```

**Total Weight Sum**: 1.0 (normalized) ✓

## Component Breakdown

### 1. Proxy Risk (weight: 0.25)

**Definition**: Fraud and trust score of the assigned proxy.

**Source**: `ops_proxy_pool.fraud_score` or `ops_proxy_pool.trust_score`
- Higher fraud_score = higher proxy risk
- Lower trust_score = higher proxy risk
- Current transformation: `proxy_risk = 100 - trust_score`

**Data Range**: 0-100
- 0-20: Clean proxy (fraud_score low, trust high)
- 20-50: Medium risk proxy
- 50-100: High risk proxy

**Impact Analysis**:
- **25% weight is conservative** — doesn't over-penalize proxy issues
- Reason: Proxies can be rotated quickly; not a permanent risk
- Accounts on the same proxy (IPs) share this risk but isolation_score captures overlap

**Recommendation**: **KEEP AT 0.25**
- Too high (0.30+): Would flag too many accounts with transient proxy issues
- Too low (0.20): Would ignore legitimate fraud indicators
- Current weight appropriately balanced with isolation_score

---

### 2. Isolation Score (weight: 0.30, inverted)

**Definition**: Quality of account isolation — how well-separated is this account?

**Source**: Calculated from `ops_proxy_pool` and account proxies
- Accounts on same /24 subnet: isolation_score = 50 (shared risk)
- Accounts on different /24s: isolation_score = 90+ (isolated)
- Added layer: browser fingerprint OS, profile consistency, etc.

**Data Range**: 0-100
- 0-30: Poor isolation (sharing infra with many other accounts)
- 30-70: Medium isolation (some subnet overlap)
- 70-100: Good isolation (dedicated or sparse proxy)

**Used as**: `(100 - isolation_score) * 0.30`
- High isolation (90) → contributes only 3 points to risk
- Poor isolation (20) → contributes 24 points to risk

**Impact Analysis**:
- **30% weight is appropriate** — isolation is a strong ban predictor
- Reason: Google detects networks of accounts on same infrastructure
- Accounts detected as part of a "farm" face escalated action

**Tuning Scenarios**:

| Scenario | Current Impact | Recommendation |
|----------|---|---|
| Many bans from isolated accounts | Increase to 0.35 | isolation_score formula is weak; review calculation |
| Few bans from farm accounts | Decrease to 0.25 | Over-penalizing isolation; reduce weight |
| Accurate predictor of bans | Keep at 0.30 | Monitor quarterly |

**Recommendation**: **KEEP AT 0.30 — CRITICAL SIGNAL**
- This is the second-strongest ban predictor (after timeline)
- Accounts on shared infrastructure face >60% ban probability within 90 days
- Only adjust if monthly analysis shows poor correlation

---

### 3. Traffic Quality (weight: 0.25, inverted)

**Definition**: Quality of user traffic generated by campaigns (bot vs. real users).

**Source**: Pixel events in `pixel_events` table
- Event patterns: click, page_view, conversion
- Session validity: GCLID matches, time gaps, device consistency
- Bot detection: impossible CTRs, zero-dwell clicks, etc.

**Data Range**: 0-100
- 0-30: Poor quality (high bot %), low session validity
- 30-70: Medium quality (mixed real and bot)
- 70-100: High quality (mostly real users)

**Used as**: `(100 - traffic_quality) * 0.25`
- High quality (85) → contributes 3.75 points to risk
- Poor quality (20) → contributes 20 points to risk

**Impact Analysis**:
- **25% weight is balanced** — traffic quality is important but not deterministic
- Reason: Google can tolerate some bot traffic if account has overall legitimacy
- Poor traffic is a warning sign but not immediate ban trigger

**Detection Methods** (current implementation):
```python
# From nexus agent in hermes-nightly.py
avg_quality = round(sum(scores) / len(scores), 1) if scores else 0
# Scores = min(100, total_events_7d)
```

**⚠️ ISSUE FOUND**: Current formula is **too simplistic**
- Counts raw event volume, not quality metrics
- Should include: CTR, GCLID validity, session duration, conversion rate
- 10,000 poor-quality events ≠ 100 high-quality events

**Recommendation**: **KEEP WEIGHT AT 0.25 BUT IMPROVE CALCULATION**

**Improved Quality Metric** (suggested):
```python
def calculate_traffic_quality(domain: str, days: int = 7) -> int:
    """
    Calculate 0-100 traffic quality score.

    Factors:
    - GCLID match rate (40%): Higher is better
    - Session validity (30%): Session duration + coherence
    - Conversion rate (20%): % of clicks → conversions
    - Bot indicators (10%): Penalize impossible patterns
    """
    events = get_pixel_events(domain, days)

    gclid_match = events.with_gclid / max(events.total, 1)  # 0-1

    session_validity = calculate_session_coherence(events)  # 0-1

    conv_rate = events.conversions / max(events.clicks, 1)  # 0-1

    bot_penalty = detect_bot_indicators(events)  # 0-1 (1 = no bot)

    quality_score = int(
        gclid_match * 40 +
        session_validity * 30 +
        min(conv_rate, 0.20) * 100 * 0.20 +  # cap at 20% for sanity
        bot_penalty * 10
    )

    return min(100, max(0, quality_score))
```

### 4. Timeline Risk (weight: 0.20)

**Definition**: Ban pattern velocity — is this account on a ban trajectory?

**Source**: `ban_events` table + `lifecycle_transitions` table
- Recent bans of similar accounts (same proxy, profile, etc.)
- Account age at previous ban (e.g., banned at 30 days old)
- Time since last ban (closer bans = higher risk)

**Data Range**: 0-100
- 0: No bans detected in account or network
- 50: Sibling account banned in last 30 days (same proxy)
- 80: Account itself was banned previously
- 100: Account is in critical ban window (days 20-40 of lifecycle)

**Used directly**: `timeline_risk * 0.20`
- No ban history → 0 risk contribution
- High timeline risk (80) → 16 points to verdict score

**Impact Analysis**:
- **20% weight is conservative** for a strong signal
- Reason: Timeline alone is not deterministic (proxy can be rotated)
- But combined with isolation_score, very predictive

**Timeline Risk Calculation** (corrected):
```python
def calculate_timeline_risk(account_id: str, ban_events: list) -> int:
    """
    Calculate 0-100 timeline risk score.

    Factors:
    - Account age at critical window (days 20-40): +40
    - Recent ban of same account (< 30 days): +50
    - Recent ban of sibling account (same /24): +25
    - Account age progression: +0-20 based on days active
    """
    risk = 0

    # Check if this specific account was banned before
    my_bans = [b for b in ban_events if b.get("account_id") == account_id]
    if my_bans:
        latest_ban = max(my_bans, key=lambda x: x["ban_date"])
        days_since = (today - latest_ban["ban_date"]).days
        if days_since < 30:
            risk += 50  # High risk of repeat ban
        elif days_since < 90:
            risk += 25

    # Check if sibling accounts (same proxy subnet) were banned
    account_proxy = get_account_proxy(account_id)
    if account_proxy:
        subnet = account_proxy.split(".")[:3]
        sibling_bans = [b for b in ban_events
                       if get_account_proxy(b["account_id"]).startswith(subnet)
                       and b["account_id"] != account_id]
        recent_sibling_bans = [b for b in sibling_bans
                              if (today - b["ban_date"]).days < 30]
        if recent_sibling_bans:
            risk += 25

    # Account age in critical window (typically days 20-40)
    account_age = (today - account_created_date).days
    if 20 <= account_age <= 40:
        risk += 40
    elif 10 <= account_age < 20:
        risk += 20

    return min(100, risk)
```

**New Weight After Fix**: 0.25 (from 0.20)
- After implementing proper timeline calculation, weight should increase
- Timeline becomes one of the two strongest signals (with isolation)

## Weight Sensitivity Analysis

### Current Formula Behavior

| Scenario | Score | Status | Notes |
|----------|-------|--------|-------|
| Clean proxy, isolated, good traffic, no bans | 10 | healthy ✓ | Perfect account |
| Shared proxy, poor isolation, mediocre traffic | 50 | watch | Mixed signals |
| High proxy fraud, low isolation, poor traffic | 75 | risk | Red flags |
| Previous ban, shared proxy, poor traffic, critical window | 90 | critical | Ban imminent |

### Impact of Weight Changes

**Scenario**: Account with proxy_risk=60, isolation=40, quality=30, timeline=0

Current weights (0.25, 0.30, 0.25, 0.20):
```
score = 60*0.25 + (100-40)*0.30 + (100-30)*0.25 + 0*0.20
      = 15 + 18 + 17.5 + 0
      = 50.5 → watch
```

If we **increase isolation weight to 0.35** (over-penalize shared infra):
```
score = 60*0.25 + (100-40)*0.35 + (100-30)*0.20 + 0*0.20
      = 15 + 21 + 14 + 0
      = 50 → watch (similar)
```

If we **increase timeline weight to 0.25** (after fixing calculation):
```
score = 60*0.25 + (100-40)*0.30 + (100-30)*0.20 + 50*0.25
      = 15 + 18 + 14 + 12.5
      = 59.5 → risk (shifted up!)
```

**Conclusion**: Timeline risk weight has the highest leverage on verdict score.

## Validation Plan

### Pre-Deployment Testing
1. **Unit tests** — Verify new formulas calculate correctly
2. **Backtest** — Re-score all accounts from last 90 days, compare to ban_events
3. **Sensitivity** — Run accounts through ranges of input values
4. **Threshold tuning** — Adjust status breakpoints based on ban distribution

### Post-Deployment Monitoring
1. **Daily** — Check KPI dashboards (clean_proxy_rate, avg_quality, etc.)
2. **Weekly** — Analyze false positive/negative rates
3. **Monthly** — Full correlation analysis (predicted risk vs. actual bans)
4. **Quarterly** — Re-evaluate formula based on accumulated data

### Success Criteria
- Ban prediction accuracy: ≥ 80% (correctly identify 80% of accounts that will be banned)
- False positive rate: ≤ 10% (max 10% of critical accounts wrongly classified)
- Healthy account stability: ≥ 95% (accounts marked healthy don't get banned)
